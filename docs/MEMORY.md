# 通用长期记忆

长期记忆由 PostgreSQL、pgvector、Pi SDK 和 Worker 提供。事实以开放的主体、属性和值保存，并保留原文出处和适用条件。

## 信息放在哪里

日程、待办、提醒是已有的权威业务记录，负责执行时间、地点、时长、状态、提前通知等参数。`今晚19点 / 大概两小时 / 提前提醒我` 不再拆成长期事实，也不从一次约会推断朋友或客户关系。

长期记忆保存可复用的个人资料、人物与组织关系、职责、偏好、约束、持续目标，以及重要事件的背景和结果。`business` 只指本应用业务对象的执行字段，不意味着所有工作或商业信息都应过滤。重要协商条件与数值可以记忆，但必须保留未确认、条件与目标状态。

例如“陈总是某个活动的负责人，约会时间下周再定”：明确职责可以本轮保存，约会时间另行澄清。通用提醒偏好也可记忆；不能因为句子含“提醒”就一律过滤。

关系可以通过 `memory_links` 引用真实 event/todo/reminder ID。展示和查询关联时读取业务对象当前状态，不把易变时间复制进事实。统一检索同时返回结构化记忆和权威业务对象。

## 三个生成入口

| 入口               | 谁判断                                 | 触发与成本                                                                                       |
| ------------------ | -------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 录音转写、转写修订 | 独立材料分析器抽取，记忆比较器决定写入 | 复用现有摘要/行动分析调用，有候选时批量比较；失败单独重试记忆，避免重做 ASR                      |
| 主会话聊天         | 当前主 Agent 自己判断                  | 遇到明确、可复用的信息，主动调用 `prepare_memory → remember_fact`；没有独立的逐消息抽取/审核模型 |
| SDK 上下文压缩     | 文件 Worker 增量补漏                   | 复用原生 compaction 边界，读取刚退出活动上下文的原始用户消息，批量抽取和比较                     |

普通聊天仅建立关键词索引。录音、明确写入的聊天证据与成功压缩扫描的来源按需建立向量。没有后台任务对每条聊天再跑一次记忆模型。确认、遗忘、置顶、人物编辑和每日归档属于维护操作，不是新的自动抽取入口。

## 归一与写入

`prepare_memory` 接收开放的 subject/predicate/value、确认状态、限定条件及原文引用链。服务端用关键词、人物、主体与向量召回相关事实，返回真实 ID、证据、状态、语义版本及关联业务对象。短引文缺少人物代词的前文时，补充附近可逐字核实的原文，再由模型判断归属。

模型选择 `ADD / MERGE / SUPERSEDE / CONFLICT / IGNORE / LINK`。聊天由主 Agent 在现有推理中作决定；录音和压缩使用批量比较器。相似度不是等价判据，关系和适用范围不依赖行业词典。“项目的负责人”与“项目负责人”可以等价，不再因抽取值不是连续子串而丢弃。

服务端验证引用的账户、来源、版本、逐字原文、记忆权限及遗忘限制。人物与组织要有证据，货币数值不能被改写，数值或币种不同不能作为同义事实合并。日期需有原文或可靠相对日期锚点，只有日期就保存日期精度，不编造时分或使用上传时间冒充发生时间。引用链可跨多条真实用户消息，助手复述与压缩摘要不能充当新证据。

`remember_fact` 只提交已准备的 proposal 与决策。目标必须来自服务端本次召回，语义版本变化则拒绝过期覆盖；重复证据不增加强度。低层规则保留给历史兼容与迁移，生产写入入口均经过语义比较。

多个爱好、朋友或职责可以并存。明确替换只修改模型选择的旧记录，确认冲突也不会替换同一属性下的其他成员。身份确实歧义时保留待确认；只有名字相同或向量相似不能合并人物。

## 确认状态与生命周期

- `certainty` 区分 stated、tentative、confirmed、goal；`qualifiers` 保留“尚未确认”等条件。未确认方案是被明确陈述的方案，不是已达成事实，也不必一律丢弃。
- 同义信息合并真实证据；明确变化替换所选当前事实，旧版本保留。晚上传的旧材料不能覆盖较新的当前值。
- 活跃度使用 `strength × 0.5^(天数 / 180)`；低于 0.2 每日归档。查询不增强强度；独立来源增强，同源重试不增强。
- 用户长期保留的记忆不衰减；明确有效期仍生效。持续目标不默认 30 天失效；标记 temporary 的阶段目标才使用默认 30 天期限。
- 当前、历史、变化过程分别检索。核心上下文最多 12 项、4000 字符；其余按需检索。
- 用户遗忘会撤回断言、清除关联向量、阻止来源重新写入并更新活动上下文 epoch。当前对含遗忘信息的整份来源保守停止自动召回；原始档案仍可主动打开。

## 压缩、可靠性和真实回执

完整会话由 SDK JSONL 和产品消息存档保留；实际模型请求使用最新压缩摘要加保留消息。例如第 7 条请求是“总结1234 + 5 + 6 + 7”。没有新建另一套聊天历史拼接器。

`memory_jobs` 持久化 compaction ID、首次保留边界、原始消息 ID、epoch、固定文段批次和游标。成功才写 `memory_scan_receipts`，重启从游标继续；不能把摘要当原文，不能把遗忘前的迟到结果写回新 epoch。失败有租约回收和有次数上限的重试。

模型 JSON 输出经 schema 校验，允许一次格式修复；比较请求最多两次，提取的传输重试同样有上限并受任务超时约束。`memory_model_runs` 记录额外抽取/比较请求与 token；聊天语义决策属于原有主 Agent 使用量。普通聊天经真实队列和全部 Worker 验证没有额外抽取、比较或 Embedding 请求。

`operations.memory_summary` 来自实际工具回执，区分未请求、仅准备未提交、已处理、已写入和失败。录音交接附带记忆任务状态；未完成不能声称已经记住。记忆页显示待处理和失败数量，支持按当前用户重试。

## 旧数据整理

`pnpm memory:reclassify` 先列出待处理数量；`pnpm memory:reclassify --apply` 为旧事实和被旧子串规则忽略的候选创建幂等整理任务。需要先备份数据库和数据卷。

模型重判业务碎片后归档并从长期记忆列表排除；丢失的限定条件可依据同一份原文更正并保留旧版本。时间未知的旧录音不会因整理而被补造发生日期。`RECLASSIFY` 事件保留原记录与决定，任务记录进度；这不是用户遗忘，不清空 SDK 会话，也不删除原文、日程、提醒或聊天。

## 验证

`pnpm test:memory` 覆盖记忆生命周期，`pnpm test:memory:semantic` 覆盖语义契约、队列、压缩游标和数据整理。`pnpm test:context` 覆盖 SDK 原生上下文压缩。`pnpm test:memory:live` 和 `pnpm test:memory:conversation:live` 使用合成中文样例与实际供应商验证，运行会产生模型用量。
