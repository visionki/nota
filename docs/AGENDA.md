# 日程、待办与提醒

日程和待办是事项主体，日历与列表是同一数据的不同视图。提醒属于事项的通知设置；自动任务属于到点执行 AI 工作的独立功能。

## 分类与时间含义

| 类型     | 意图                                           | 时间                                 | 状态                              |
| -------- | ---------------------------------------------- | ------------------------------------ | --------------------------------- |
| 日程     | 已约定发生的安排，例如聚餐、已预约看牙         | 明确开始，结束可省略；或全天日期     | confirmed / cancelled             |
| 待办     | 需要完成的行动，例如尚未预约的拔智齿、提交方案 | 可选计划日期/时段、可选截止日期/时刻 | open / done                       |
| 提醒     | 通知某个事项                                   | 固定时刻，或相对主体时间的提前量     | scheduled / delivered / cancelled |
| 自动任务 | 到点让 AI 执行工作                             | 一次或周期                           | 启用 / 停用                       |

“两周后去拔智齿，尚未预约”保存为有计划日期的待办，不推断具体时刻或截止日期。“已约11月27日9点拔牙”保存为日程，结束未知可以不填。同一行动不自动创建两份主体。“6点叫醒我”可保留为独立提醒，不附带日程或待办。

## 数据与接口

- 待办：`planned_date` 与 `planned_at` 二选一；`planned_end_at` 可为有时刻的计划预留时段。`due_date` 与 `due_at` 二选一。所有时间可为 `null`，仅日期使用 YYYY-MM-DD，不转换为默认9点。`timezone` 默认账号时区。
- 日程：有时刻时传 `starts_at`，`ends_at` 可省略或为 `null`。全天使用 `all_day=true, starts_on=YYYY-MM-DD`，可选 `ends_on` 不含结束当日，省略时为单日。数据库保留当地午夜边界用于查询，但界面与导出使用日期精度。
- 创建主体可传 `reminders` 数组；修改主体可传 `add_reminders` 数组追加提醒。主体与这些提醒在同一事务保存，任一失败全部回滚。
- 提醒关联 `event_id` 或 `todo_id`，最多一个。固定时刻传 `remind_at`。相对提醒传 `before_minutes` 和 `relative_to=start/end/planned/due`；仅日期不能作为相对时刻基准，需另行明确通知时刻。
- `GET /api/todos/:id` 和 `GET /api/calendar/:id` 返回主体与全部提醒历史。`GET /api/todos` 返回待办与关联提醒。`GET /api/agenda` 返回区间内日程、计划/截止待办、无日期待办及相关提醒设置，包括通知时间位于区间外的关联提醒。
- 日期字段由 PostgreSQL 以字符串读取，避免服务器时区把日期移动到前一天。部分更新不应用创建默认值；显式设置一种日期精度会清除另一种精度。

## 视图

- 日历直接展示日程与有日期的待办，不依赖提醒存在。仅日期事项进入全天区域，有时刻事项进入周时间轴。
- 待办的计划与截止不在同一天时，分别显示“计划”和“截止”节点，均引用同一待办 ID；在同一天时合并为一项，详情列出两个时间。
- 关联提醒不单独绘制日历卡片，无论提前多少天、设置多少条提醒。独立提醒才作为独立条目显示。
- 日历可勾选完成/恢复待办；已完成待办默认隐藏，可开启显示。全部事项列表按当前月/周列出事项，并包含无日期待办；待办清单不自动收录日程。
- 新建事项明确选择日程、待办或独立提醒；有无结束时间不改变事项类型。编辑保持原对象身份。

## 生命周期与并发

- 完成待办或取消日程：取消尚未投递的所有关联提醒，已发送通知保留历史。恢复待办不会重新创建或启用旧提醒。
- 改期：只重新计算相对提醒，固定时刻不动。清除相对提醒的基准时刻，或调整后提醒已过期，取消该提醒；自定义提醒标题保留。
- 单独修改提醒 `remind_at` 会切换为固定时刻；明确传提前量则切换为相对提醒。已投递/取消提醒只读。
- 主体修改和投递 Worker 都先锁主体，再锁提醒。投递前核对主体仍未完成/取消，并复核提醒归属，防止完成与通知竞争导致过时通知。

## Agent

`create_event/create_todo`、`update_event/update_todo` 公开上述完整字段和事务内提醒参数。`get_todo` 和 `get_event` 每次读取最新状态，主 Agent 和后台查询都可调用。

主 Agent 与录音分析器共享分类规则：按约定/行动/通知意图区分，计划和截止分开，保留仅日期精度，不猜时长，同一事项不重复创建。只有用户明确要求通知才创建提醒。关联提醒使用真实主体 ID；已有记录原地修改。

录音行动候选与来源限制仍生效，事项内嵌提醒也检查来源的提醒权限，不允许绕过“不要创建提醒”的范围限制。自动任务与普通通知保持分离。

候选的日程/待办类型是分析建议，主 Agent 可根据原文复核纠正，但保留 `candidate_id`；执行主体、明确交办、批次、原文版本及整理范围仍须校验。实际创建类型保存在 `result_type`，重试返回同一对象，已创建待办后不能再为同一候选创建日程。提醒不能与事项主体互换。仅传来源时，工具会匹配当前批次的已有候选并沿用同样的校验和回执关联，不能通过省略候选 ID 绕过拒绝；匹配到多个行动时需明确候选。没有已知候选的新行动仍可使用有效来源。工具失败返回具体错误码，区分主体归属、未明确交办、范围限制、类型冲突和已执行。

## 迁移与导出

迁移新增字段并保留原有对象 ID、标题、时间、完成状态、来源和会话，不按猜测重解释旧截止时间。历史关联日程提醒按原有改期行为初始化为相对开始提醒；新增固定提醒不会在重复迁移时被改写。旧独立提醒仅在“同账号、同操作、通知时刻恰好等于唯一待办截止时刻”时恢复其待办关联，不按标题模糊匹配。

ICS 导出包含 VEVENT、VTODO 及其 VALARM，关联提醒不再生成额外事件；独立提醒以带通知的单点事件导出。全天使用 VALUE=DATE。VTODO 的计划/截止精度不一致时，按标准保留截止精度，将计划保存在 X-NOTA 元数据中，不虚构时刻。

## 验证

`pnpm test:agenda` 使用独立临时数据库覆盖日期精度、日历投影、原地修改、提醒归属、改期、完成/恢复、投递竞争、事务回滚、HTTP/真实工具契约和旧版迁移。`tests/browser/agenda-model.spec.ts` 覆盖 PC/H5 创建、日历完成、恢复、列表、时段与全天区域。`pnpm test:agenda:live` 可选，使用合成文本和独立数据库调用真实 Pi/GMI，产生模型用量。
